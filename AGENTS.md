# remnashop — AGENTS.md

Project rules for everyone who changes this repository, people and AI agents alike. `CLAUDE.md` imports this file; other agents (Codex, Cursor, Copilot, Gemini CLI) read it directly. The PR process is in [.github/CONTRIBUTING.md](.github/CONTRIBUTING.md). Keep rules here, not in tool-specific files.

Telegram bot for selling VPN subscriptions, integrated with [Remnawave](https://github.com/remnawave). The project is being rebuilt dashboard-first: a React admin panel becomes the primary way to administer the shop, the Telegram bot becomes an optional, dashboard-configurable client channel.

**Stack:** Python 3.12, aiogram 3.x, aiogram-dialog, FastAPI, Dishka DI, SQLAlchemy async, asyncpg, Alembic, Redis, taskiq, Fluentogram, remnapy SDK — backend. React + Vite + TypeScript, Tailwind CSS, react-router — frontend.

---

## Topology

Monorepo, two independent subprojects: `backend/` (own `pyproject.toml`/`uv.lock`/`tests/`) and `frontend/` (own `package.json`). `.env`/`.env.example` live at the **repo root**, not inside `backend/` — `docker-compose` picks up `.env` next to itself by convention, and it's the single source of truth for every future process.

Backend runs as independent processes, each its own composition root:

- **`api`** (`app/api/`) — the single HTTP/REST process. Serves both public customer-facing endpoints and admin/dashboard endpoints on the same FastAPI app; the split is by router (`modules/<domain>/api/public_router.py` vs `admin_router.py`) and by dependency (`api/dependencies/public.py` vs `admin.py`), not by separate services. `public_router.py`/`public.py` mean "requires a valid session, role doesn't matter" (`get_current_actor`) — not "no auth at all." Two dependencies live there: `get_current_actor` (a session **or** an API token, for routes that only need *someone* authenticated) and `get_current_user` (a real `UserDto` only, 403 for an API token) — customer self-service routes that act on the actor's own identity (checkout, promocode activation, referrals) use the latter, since a token has no customer row behind it and would otherwise reach them as user id 0. Staff routes acting on the caller's own account (`/users/me*`, passkeys, own sessions, OAuth connect, notifications, test payments) use `api/dependencies/admin.py`'s `require_admin_user` — `require_admin` plus the same check. The usecase behind such a route declares `UseCase[InputDto, OutputDto, UserDto]` (third parameter defaults to `core.actor.Actor`), so mypy refuses a call with anything but a real user; `Actor` itself carries only identity and permission fields. A route reachable with zero session (like auth's own bootstrap/login/status, which can't require a session since they're what produces one) doesn't belong in either file; give it its own `router.py`, as `modules/auth/api/` does.
- **`telegram`** (`app/telegram/`) — optional client bot, webhook mode (not long-polling). No admin logic lives here. Bot token/webhook secret are dashboard-configured (`modules/settings/`, encrypted at rest), not env — read once at process startup (`__main__.py`'s `if __name__ == "__main__":` block, before `uvicorn.run()`), no hot-reload. If unset, the process serves a minimal idle app (`GET /health` only) instead of crashing — restart the process after setting the token via the dashboard.
- **`worker`** (`app/worker/`) — taskiq worker, run via the native `taskiq worker` CLI (`docker-entrypoint.sh`). `app/worker/container.py` builds its own Dishka container from the same `get_core_providers()` + `app/modules/providers.py`'s `get_module_providers()` as `api` and `telegram` (every process gets the whole graph; `tests/worker/test_container.py` resolves every task's `FromDishka` dependency and checks the entrypoint lists every `tasks.py`); `app/core/broker.py` is a `taskiq_redis.ListQueueBroker` — in `core`, not `worker`, since `api` and `telegram` enqueue through it too; `tasks.py` never imports `app.worker`. Worker tasks live in each module's `tasks.py` as thin adapters: deserialize the message, take a system usecase (`required_permission = None`, reachable only via `.system`) through `FromDishka`, call it — plus a `cron_lock` where a schedule must not overlap itself; no repositories in a task. Every such module is listed on the `taskiq worker` command in `docker-entrypoint.sh` — `event_log` (outbox → audit log), `subscriptions` (purchase/renewal, `process_remnawave_webhook_task` — the api only verifies a panel webhook and queues it, the worker syncs the subscription, retries a failed sync and skips an event older than the last one applied to that panel user — and `run_panel_sync_task`: an admin-started sync of every subscription from or to the panel — nothing polls the panel on a schedule, webhooks carry its changes), `transactions` (expired-transaction pruning, paid-transaction reconciliation, `confirm_stars_payment_task`, the fallback when the bot's `successful_payment` handler can't settle the order in place), `auth` (stale sessions), plus `referrals`, `backups`, `blacklist`, `advertising`, `announcements` (syncs the public GitHub feed on a taskiq `interval` schedule, which fires when the scheduler starts), `overview`, `notifications` (delivers grouped events to admins by web push and Telegram), `email` (SMTP delivery of sign-in codes and the test email; an optional bulk SMTP profile and per-minute rate for broadcasts), `customer_notifications` (a `notify_customer_task` per customer-facing event, queued by its subscribers, plus a retried `send_customer_telegram_task`), `broadcasts` (customer broadcasts: start/materialize one recipient row per channel, paced Telegram delivery batches and a separate paced email chain over one SMTP connection per batch, recall, a `*/1` tick that starts due broadcasts and re-kicks stalled ones, daily recipient pruning), `users` (hourly blacklist reconciliation), `promocodes` (hourly warning about expiring promocode discounts), `loyalty` (nightly loyalty-discount recalculation, plus an on-demand run through `LoyaltyRecalcDispatch`). A new `tasks.py` isn't picked up until it's added there; one with a `schedule=` task goes on the `taskiq scheduler` command too (that command reads schedules only from the modules it imports). The worker runs `WORKER_PROCESSES` (default 1) processes, each with its own DB pool and at most `WORKER_MAX_ASYNC_TASKS` (default 25) tasks at once, below that pool, so a burst queues in Redis instead of timing out on the pool; compose sets Postgres `max_connections` from `DATABASE_MAX_CONNECTIONS` (default 200) to fit the three processes' pools.
- API docs (Swagger at `/api/v1/docs`, ReDoc at `/api/v1/docs/redoc`, schema at `/api/v1/docs/openapi.json`) follow Remnawave's backend-tools gate: the dashboard trades a session for a 30-second ticket (`POST /api-tokens/actions/issue-ott`, `API_TOKENS_MANAGE`), `?ott=` trades the ticket for a 2-hour httponly cookie scoped to the docs path. No env flag.
- `COMPOSE_PROFILES=admin-api` starts a second `api` container (`remnashop-admin-api`, `127.0.0.1:${ADMIN_API_PORT:-5002}`, `APP_INSTANCE_NAME=admin`) that the reverse proxy routes the dashboard's domain to, so a flood on the cabinet, the bot or the panel webhooks leaves the dashboard answering.
- With `APP_METRICS_ENABLED=true` (off by default), both `api` (`GET /metrics`) and `worker` (`GET :{APP_METRICS_PORT}/metrics`) expose Prometheus text-format metrics, unauthenticated — same trust model as `/health`/`/readyz`. **Block both at the reverse proxy in production**; nothing in the application itself restricts access. Full metric catalog and the two-registry pattern: [docs/architecture/observability.md](docs/architecture/observability.md).
- **`cli`** (`app/cli/`) — break-glass tool, run via `docker compose run --rm remnashop cli` (the entrypoint's `cli` target: a fresh container without migrations or the `APP_CRYPT_KEY` check, so it works while `api` crash-loops), mirrors Remnawave's own rescue CLI. Legacy-version upgrade (`app/cli/legacy/`): a database of the old `src/` app (legacy alembic `0001`–`0046`, vendored in `app/cli/legacy/migrations/`) is migrated automatically when `api` starts (`app/cli/legacy_guard.py`, first step of the entrypoint's `api` branch): preflight (panel 3.x, `APP_CRYPT_KEY` trial decrypt) → signed `DATABASE_pre-legacy-migration_*` dump → panel index (shortUuid → `rs_<tg>`/`rs_web_<id>` → unique telegramId) → legacy chain to `0046` → one transaction (`public` → `legacy`, new schema via `upgrade head`, pure per-table transforms, ids kept) → report → Redis `FLUSHDB`; a failure after the dump leaves `backups/legacy-migration-failed.txt`, a revision in neither chain is refused without a dump. The migrated owner has no login and `OAuthSettings.owner_claim_pending` set: `POST /auth/bootstrap` claims that row instead of creating one. The menu also has "Migrate data from the old version" (manual), "Roll back the migration", "Delete old-version data". Rescue actions: "Enable password authentication", "Restore backup" (`app/cli/restore_backup.py`, provenance check + `pg_restore`), "Reset owner access" (`app/cli/reset_owner_access.py`: new generated password, cleared `ip_allowlist`, all sessions revoked, passkeys and linked OAuth identities removed (API tokens kept), password login re-enabled — the way back in after an IP-allowlist or credential lockout), "Reset encrypted secrets" (after `APP_CRYPT_KEY` changed: clears every encrypted column — bot token and proxy, gateway credentials with the gateways switched off, OAuth clients, SMTP passwords, captcha secret, web push keys — to be entered again in the dashboard). No bootstrap-owner action: the dashboard's own `POST /auth/bootstrap` covers it while no `OWNER` exists.

## Modular monolith rules

Top level under `app/` is organized **by domain**, not by technical layer: `modules/<domain>/`. Each module is self-contained. For what each module currently owns and how they actually depend on each other, see [docs/architecture/context-map.md](docs/architecture/context-map.md).

```
modules/<domain>/
├── __init__.py     # public interface — the ONLY thing other modules may import; exports only names some other package imports (tests/test_module_interfaces.py)
├── dto.py
├── repository.py   # plain concrete class, no Protocol — never substituted in a test
├── usecases/       # one file per operation (Cosmic Python/Remnawave granularity); tests import from here or the defining file, not the package
├── di.py           # dishka Provider registration
└── api/
    ├── admin_router.py
    ├── public_router.py
    └── schemas.py
```

- **Boundary rule:** a module reaches another module only through its public `__init__.py` interface — never through another module's `repository`/`models` directly. Enforced by `import-linter` (`backend/.importlinter`'s `module-boundaries` contract, a custom type in `backend/import_contracts.py` that covers every child of `app.modules` automatically: `app.modules.<domain>.*` importable only from the module itself and the `app.api.routers`/`app.worker.subscribers` composition roots) as part of the standard verification command, not just review discipline.
- **Two-way need between modules:** the lower module (the consumer) declares a `Protocol` in its own `ports.py`, exported from its `__init__.py`; the higher module, which already imports it, implements the port and binds it in its `di.py`. `core/ports.py` holds only cross-cutting infrastructure ports (`EventPublisher`, `OutboxEntryDispatch`, `BotSignals`, translators) — no domain vocabulary. An import back would fail `modules-acyclic`; an event works too when the caller needs no answer.
- **Imports are always absolute** (`from app.modules.settings.dto import ...`), never relative (`from .dto import ...` / `from ..dto import ...`) — including within a module's own package. Enforced by ruff's `TID252` (`ban-relative-imports = "all"`), part of the standard verification command.
- **SQLAlchemy models are centralized** in `core/db/models/`, not inside each module — see [docs/architecture/db-models.md](docs/architecture/db-models.md).
- **Telegram presentation is centralized** in `app/telegram/<domain>/`, not `modules/<domain>/telegram/`. Unlike `api/` (mandatory, universal, one process), the bot is optional and covers only part of the modules — keeping it in one place answers "what do I touch if the bot is disabled" cleanly. Business logic (dto/repository/usecases/api) stays in the module regardless of channel; only the aiogram-dialog UI glue lives under `app/telegram/`.
- **Bot window texts**: `msg-*`/`frg-*` values are Telegram HTML, rendered only through `telegram/dialogs/rendering.py`'s `render_window_text`. Variable values are escaped; ready-made blocks are `TrustedHtml` rendered from `frg-*` keys. A line holding an empty variable is dropped and its tags kept (a pair opened and closed on that line goes with it); if nothing visible remains, the text renders again with the lines kept and the values empty. HTML is validated on write: by key prefix in `translations`, through `validate_window_text` in `dialogs`, both with `core.utils.telegram_text.validate_telegram_html`. Variables available to only one window are declared in `CatalogWindow.text_variables`. `banner_within_caption` drops the banner when the text exceeds the caption limit.

**Per-layer conventions** (how to write each piece, with code examples): [repositories](docs/architecture/repositories.md) · [usecases](docs/architecture/usecases.md) · [DI/providers](docs/architecture/di-providers.md) · [API routers](docs/architecture/api-routers.md) · [DB models](docs/architecture/db-models.md) · [events](docs/architecture/events.md) · [permissions & roles](docs/architecture/permissions-roles.md).

## API conventions (mirrors Remnawave's REST shape)

- **Errors:** every domain exception (`core/exceptions.py`) carries a mandatory `code=ErrorCode.X` (`core/error_codes.py`); `api/errors.py`'s global handler maps the class to a status and answers `{"detail", "code"}` — routers don't catch-and-remap, they only catch to *change* a status. API-layer errors with no domain exception behind them use `api.errors.ApiError`. Each code needs `apiErrors.<CODE>` in both frontend locales (enforced by `tests/api/test_errors.py`); the dashboard translates by code, falling back to `detail`.
- **Response mapping:** `XResponse.model_validate(dto, from_attributes=True)` — the schema is the allowlist of what leaves the API; hand-written mappers only where a value is computed (dialogs' `text_keys` from the catalog); a fallback or a format conversion is a `field_validator(mode="before")` on the schema, a derived number a property on the DTO.
- **OpenAPI:** `responses=error_responses(...)` on each route; 401/403 are derived from the `get_current_actor` dependency, 422/429 are global. `operationId` = handler function name (unique across routers).
- **URLs:** non-CRUD actions are `POST .../actions/<verb>`, bulk ones `POST .../bulk/<verb>`; protocol steps (`auth/login`, OAuth `callback`, passkey `options`/`verify`) stay bare verbs, like Remnawave's. Resetting something to defaults is `POST .../actions/reset` (200 + the new state), never `DELETE` — the resource still exists afterwards. Sub-resources of one user live under `/users/{user_id}/...` (sessions, referrals, ...); the actor's own login-related ones stay under `/auth/...`. Payment/Remnawave webhook URLs are configured in external systems — never rename them.
- **Methods & statuses:** creating a new entity is `POST` → 201. An upload or value with a known address is an idempotent `PUT` to that address (`PUT /banners/{name}/{locale}`, `PUT /settings/locales/{locale}`, `PUT /blacklist/entries/{kind}/{value}`) → 200, paired with `DELETE` on the same path — never a `DELETE` with a body. All-optional partial updates are `PATCH`; a plain flag (`is_active`, `enabled`) is a `PATCH` field. Explicit `actions/enable`/`actions/disable` only when switching on has a side effect or a check (gateways), never `toggle`.
- **Responses:** never a top-level array — collections are `{items, total}` (a per-endpoint `XListResponse` model; paginated ones add `page`/`page_size` params), `actions/reorder` returns the same shape as its list, a settings value is an object (`{commands}`, `{lines}`) and GET/PUT on one path share one model. Every catalog entity an admin opens one at a time (users, plans, promocodes, subscriptions, addons, transactions, ad links, blacklist sources) has `GET /{id}` gated by its own `*_DETAIL_VIEW` permission — own-account sub-resources (sessions, passkeys, API tokens) and dialog windows are list-only by design; numeric path params use `{id:int}` so they can't shadow sibling static routes (`/users/me`, `/plans/catalog`).
- **Date filters:** `<column>_from`/`<column>_to` named after the filtered column (`created_*`, `occurred_*`), half-open `[from, to)` compared with `<`; wherever `_from` exists `_to` exists too. A bare date as `_to` means the whole day (`core.utils.time.range_end_utc` → next midnight).
- **Consistency:** `error_responses(...)` lists every status the route and its usecase can answer (never 422/413/429, those are global). A route's actor annotation is the type its dependency returns (`UserDto` for `*_user`, `Actor` otherwise). `DEFAULT_PAGE_SIZE`/`MAX_PAGE_SIZE`/`SEARCH_MAX_LENGTH` come from `core.constants`; a paginated response is `XPageResponse{items, total}`, every other collection `{items, total}` plus side fields. A flag is named the same in the request and the response (`github_enabled`); only a computed state is `is_*_configured`. Update DTOs are built with explicit keyword arguments. `/users/{id}/...` routes live on a module's `user_router` (prefix `/users`); a router without a session is exported as `router`. Routers only translate HTTP: no defaults, choices or truncation decided there. Unknown request fields are ignored everywhere (no `extra="forbid"`). Every route model is a `*Request` or `*Response` (nested ones too) declared in `api/schemas.py` (`app/api/system_schemas.py` for the system router), never in a router file; import and export are separate models even when their shapes match. Exceptions: `users/schemas.py`'s `UserResponse` (shared with `account_merge`, and importing `users.api` would pull in the routers), `auth/session_response.py`'s `AuthResponse` (returned by the auth, oauth, passkeys and cabinet_auth routers, same reason), `subscriptions/plan_snapshot_response.py`'s `PlanSnapshotResponse` (returned by the subscriptions and transactions routers, same reason) and broadcasts' value DTOs nested in its schemas. A route raises `ApiError`/a domain exception, never `HTTPException`.

## Usecases: two patterns, distinguished by inheritance, not naming or folder

A usecase's input and output types are `*Dto` classes in the module's `dto.py` — never declared inside a `usecases/` file and never `*Input`/`*Result`; a file in `usecases/` holds the usecase and its private helpers only.

Both patterns live in the same `usecases/` package — the split is purely "does this subclass `UseCase`," not a naming or folder convention. Post-authentication (the common case, `core.usecase.UseCase[InputDto, OutputDto]`) vs pre-authentication (plain DI-injected classes with `execute()`, no actor, no `UseCase` base, since there is structurally no actor yet at this point): `modules/auth/` for bootstrap/login/status, and `modules/settings/`'s `GetPublicAppearanceUseCase`/`GetPublicAppearanceImageUseCase` for the same reason — the logo/favicon shown on the pre-login page. Clean Architecture treats "Interactor" and "Use Case" as synonyms; this project doesn't — see [docs/architecture/usecases.md](docs/architecture/usecases.md) for the terminology note, the `UnitOfWork.commit()` rule, and code examples.

### Usecase rules

- **Another user's account**: get the target with `users.get_visible_target(repo, actor, user_id)` (hidden staff → 404; `for_update=True` locks the row and skips anonymized accounts), then `users.assert_manageable(actor, target)` for a write. No other staff check, no 403/409/422 for an out-of-reach account.
- **Transactions**: every repository call sits inside `async with self._uow`; check and write share one transaction. A second unit of work only wraps an external call (panel, gateway, file) or the idempotency claim. Exception: revoking access (`PanelSubscriptionRevoker`) deletes the panel user inside the caller's locked transaction, panel first — the database must never say access is gone while the VPN still works.
- **Network calls and locks**: a call to a payment provider, SMTP or any third-party API never runs while a transaction is open or a row is locked — persist the claim (idempotency key, pending row) and commit, call, record the outcome in a second transaction. A Remnawave panel push may run under the subscription's row lock only where that lock is what keeps the panel and the row consistent (an addon grant racing a plan change, revocation); say so in a comment at the call.
- **Audit events**: every admin write publishes an event in the transaction of its write — `ActorEvent` for staff actions, `ActorTargetEvent` when they act on a user, `UserEvent` only for a user acting on their own account. One class per area with an `action` field (`PlanChangedEvent(action=...)`), not one per operation. A partial update records `changed_fields(before, after, names)`. Admin and security inputs carry `client_ip: str`, published as `ip_address`.
- **Inputs and outputs** are `*Dto` from `dto.py`; only an entity id or a path key (`Locale`, `OAuthProvider`, `PaymentGatewayType`) stays bare. A composite result is a named DTO; the one allowed tuple is `(items, total)`.
- **Layout**: one usecase per file, named after the class without `UseCase` (subclasses that only change `required_permission`/audience of another usecase may share one file, as `notifications/usecases/customer_push.py` does). Code two or more usecases share lives in a module file outside `usecases/` (or `usecases/_<name>.py`); usecase files don't share helpers with each other; a usecase may inject another usecase of its own module and call it through `UseCase.__call__`/`.system()`. Routers, tasks and DI import from `<module>.usecases`, other modules from `<module>/__init__.py`.
- **Naming**: an injected usecase is `<operation>_use_case`; a dispatch is scheduled as `await self._uow.after_commit(partial(self._x_dispatch.kiq, ...))`; an action log reads `f"{actor.log} <Verb> <what> '<id>'"`.

## Auth

- Login+password, plus OAuth (GitHub, generic OIDC, Telegram, Google, Yandex — `OAuthProvider`) via `modules/oauth/` (provider adapters, identity linking, the dashboard's OAuth-connect routes; sign-in through a provider, for the dashboard and the cabinet alike, is `cabinet_auth`'s zero-session `/auth/oauth/{provider}/authorize`/`callback` with an `audience` field), plus WebAuthn passkeys via `modules/passkeys/`. Passkey settings (`passkey_enabled`, `passkey_rp_id`, `passkey_origin`) live in `OAuthSettings`; own-account passkey CRUD uses `Permission.OWN_ACCOUNT_MANAGE`. Passkey login resolves the user via the credential's own discoverable `credential_id` (usernameless), not via a fixed admin. Passkey verification accepts both `passkey_origin` and `https://{passkey_rp_id}` as the expected origin. Telegram OIDC's `id_token` payload is decoded without signature verification — the token response is fetched server-to-server over TLS and the exchange is already authenticated by `client_secret`. `POST /auth/bootstrap` creates the single `OWNER` (only while none exists — enforced by a Postgres partial unique index on `role`, not just an app-level check, since the app-level check alone is TOCTOU-racy). `POST /auth/login` for repeat sign-in. `GET /auth/status` tells the frontend which form to show.
- Same generic `401 Invalid login or password` whether the login doesn't exist or the password is wrong — never leak which case it was (no user enumeration).
- Password hashing: scrypt + HMAC pepper (`core/security/password.py`), pepper = `APP_CRYPT_KEY`. JWT signing (`core/security/jwt.py`) = `APP_JWT_SECRET`, HS256, payload `{sub, sid, exp}` (`sid` ties the token to a `user_sessions` row, no `role` claim), short-lived (`TTL_15M`). Both patterned after Remnawave panel's own `auth.service.ts` (see docs links below) with deliberate deviations noted inline where we didn't copy them 1:1 (e.g. we use `APP_CRYPT_KEY` as pepper, not the JWT secret — matches what that key's own name says it's for).
- Sessions & refresh tokens: `modules/auth/session_issuer.py` issues an access token plus a refresh token per session (`core/db/models/user_session.py`, `SessionRepository`). `POST /auth/refresh` rotates the refresh token with a grace window; reuse outside that window is treated as theft (`SessionTheftDetectedEvent`, session revoked). `POST /auth/logout` and admin-triggered revocation (`/users/*/security`) exist. Refresh token lives in an `httponly` cookie, not `localStorage` — only the short-lived access token does.
- `api/dependencies/public.py`'s `get_current_actor` returns `core.actor.Actor` (a `Protocol`), not `UserDto` directly. It decodes the bearer credential as a session JWT first; if that fails, it falls back to resolving the credential as an API token (`ApiTokenRepository`) and returns a `SyntheticActor` (`is_privileged=True`, `permission_grants` set from the token's own scopes) instead of raising. `admin.py`'s `require_admin` wraps `get_current_actor` with an `is_privileged` (role ≥ `ADMIN`) check — a `SyntheticActor` always passes this, since a token's real authorization boundary is its `Permission` grants inside the usecase, not the router-level role check (see [permissions-roles.md](docs/architecture/permissions-roles.md)). "Admin" here means the dashboard/staff audience generically (`ADMIN` and everything above it — `OWNER`, `SYSTEM`), not literally `Role.ADMIN` only — considered renaming to `dashboard`/`privileged`/`staff` to avoid the appearance of a collision with the enum value, decided against it (`admin` is standard enough, matches Remnawave's own precedent). Don't read `require_admin` as "only `Role.ADMIN` passes." General router-splitting/rate-limit conventions: [docs/architecture/api-routers.md](docs/architecture/api-routers.md).
- Bootstrap/login/status live in `modules/auth/api/router.py`, not `public_router.py`/`admin_router.py` — a zero-session route can't go through `get_current_actor` (no session exists yet), so it gets its own `router.py` in the module's `api/` package instead. `modules/transactions/api/router.py` (payment-gateway webhooks, `POST /payments/{gateway_type}` — path kept from `main` since it is registered in every gateway's dashboard) and `modules/subscriptions/api/router.py` (Remnawave webhook) follow the same shape for the same reason (server-to-server callback, no session to decode) — auth's `router.py` was the first instance of this pattern, not the only one. If `modules/auth/` later gets genuinely admin-gated routes (e.g. "create another admin"), those get a real `admin_router.py` alongside this one, not folded into it.
- Every route in `modules/auth/api/router.py` is rate-limited per IP via `api/dependencies/rate_limit.py` (Redis fixed-window counter): `status` 30/min, `bootstrap` 5/min, `login` 10/min, `refresh`/`logout` 30/min; OAuth sign-in lives in `modules/cabinet_auth/api/router.py` (`oauth_authorize`/`oauth_callback` 30/min, plus a 20/min failure limit on the callback), `modules/passkeys/api/router.py`'s `passkey_authenticate` is 10/min. Add the same to any future unauthenticated write endpoint.

## Settings & Secrets at Rest

- `modules/settings/` (the first DB-backed settings module) owns `BotSettings` (`core/db/models/bot_settings.py`, single row, always `id=1` — a plain get-or-create in the repository, not a DB constraint like `OWNER`'s partial index; low-stakes enough not to need one). `token`/`secret_token` are Fernet-encrypted at rest via `EncryptedString` (`core/db/encrypted_string.py`, a `TypeDecorator` keyed by `APP_CRYPT_KEY`) — encryption/decryption happens transparently at the column level, so the ORM row is always plaintext above the DB. `BotSettingsDto.token`/`.secret_token` (and `OAuthSettingsDto`'s three `*_client_secret` fields) are `pydantic.SecretStr`, not plain `str` — masked from `repr()`/`str()`/exception traces, unwrapped with `.get_secret_value()` only at the point of use, same discipline as the env-level secrets below. `GET /settings/bot` only ever returns `is_configured: bool`, never the token itself, even to an authenticated admin — write-only from the API's perspective, matching how you'd treat a password field.
- Gated by `Permission.BOT_SETTINGS_MANAGE` through the normal `UseCase` path (`GetBotSettingsUseCase`/`UpdateBotSettingsUseCase`) — this is the first real use-case-based module beyond the `GetCurrentUserUseCase` proof-of-concept, and the first real DB write to go through `UpdateBotSettingsUseCase`. Its transaction is what makes the write durable — this exact class of bug shipped once already (`update_bot_settings` had no committing caller, silently lost on teardown) and was only caught by a live cross-process test (API writes it, restart the `telegram` process, check it's still there), since a same-transaction unit test can't see the difference between flush and commit. `UnitOfWork` now auto-commits on a clean `async with` exit specifically so this can't recur structurally. General repository/usecase write conventions: [docs/architecture/repositories.md](docs/architecture/repositories.md), [docs/architecture/usecases.md](docs/architecture/usecases.md).
- `telegram/__main__.py` reads the token via `modules.settings.read_bot_settings()` — a standalone, throwaway `AsyncSession`/engine, not the process's dishka container (the container's own construction needs `Bot`, which needs the token — this read has to happen first, chicken-and-egg). Called with `asyncio.run()` from the true `if __name__ == "__main__":` entry point, *before* `uvicorn.run()` — calling it inside a `factory=True` app callable fails, because uvicorn invokes that callable synchronously from inside a loop it already owns (`asyncio.run()` inside there raises "cannot be called from a running event loop"). This is why `telegram/__main__.py` builds a concrete `FastAPI` instance up front and passes it to `uvicorn.run(app=<instance>, ...)` instead of using `factory=True` like `api/__main__.py` does.
- `BotSettings.proxy_url` (encrypted, write-only like the token — the API only exposes `is_proxy_configured`; `PUT`/`DELETE /settings/bot/proxy`) routes **every** Telegram API call through a proxy: the bot's `AiohttpSession` in `telegram/__main__.py`, and every call from `api`/`worker`, which goes through `core.telegram_api.bot_client(token, proxy)` (`proxy` is a required argument, so a new call can't forget it). Accepted schemes are what aiohttp-socks parses (`set_bot_proxy.py`'s `_PROXY_SCHEMES`, guarded by `tests/telegram/test_proxy_schemes.py`).
- `NotificationSettings.vapid_private_key` (web push) is `EncryptedString` too and write-only: `GET /notifications/settings` returns only the public key; keys are generated in the dashboard, never set via env.
- `BOT_TOKEN`/`BOT_SECRET_TOKEN` env vars are gone (removed from `BotConfig` and `.env.example`) — a fresh deployment has no bot until someone logs into the dashboard and sets it via `PATCH /settings/bot`. `BotConfig` keeps only `host`/`port` (deployment-level, not dashboard-configurable).
- **Applying a settings change**: still no in-process hot-reload (matches the earlier decision — see Topology) but there's now an explicit **"Restart bot" button** (`POST /settings/bot/actions/restart`, `RestartBotUseCase`) instead of requiring a manual process restart. It signals through the `BotSignals` port (`core/ports.py`; `core/bot_signals.py` publishes on `core.constants.TELEGRAM_RESTART_CHANNEL` via Redis pub/sub, fire-and-forget — a no-op if nothing's subscribed), the same port dialog and translation edits use to reach the bot; `app/telegram/bot_signals.py`'s `listen_for_bot_signals()` runs as one background task in *both* the idle app's (restart only) and the real app's lifespan, and on receiving the message sends itself `SIGTERM` so uvicorn's normal graceful-shutdown path runs (dispatcher shutdown events, `endpoint.shutdown()`, etc.) rather than a hard kill. The process exiting is the whole mechanism — something else has to bring it back: Docker's `restart: unless-stopped` in production, manual restart for local `uv run` dev (no supervisor there yet). This mirrors Remnawave's own approach to node config changes — they explicitly restart the affected Xray node via a queued job rather than hot-swapping its config in place, the same "exit and let the supervisor restart you" shape, just RPC-triggered there instead of Redis-pub/sub-triggered here.

## Events

- Publishing goes through a transactional outbox, not straight to in-process subscribers. `core/outbox_event_publisher.py`'s `OutboxEventPublisher` (bound to the `EventPublisher` port every usecase injects, `Scope.REQUEST`) writes an `EventOutboxEntry` row in the *same* DB transaction as the usecase and registers a kick of the worker through `UnitOfWork.after_commit()` (the `OutboxEntryDispatch` port, implemented by `event_log`). `core/event_bus.py`'s `EventBus` itself only holds type-specific `subscribe()` handlers plus `dispatch_stored()`/`shutdown()` — it has no `publish()` of its own, and is registered as a plain `Scope.APP` singleton (`EventBusProvider`), not aliased to any port.
- `modules/event_log/tasks.py`'s `process_outbox_entry_task` (kicked once the publishing transaction commits) and `sweep_outbox_task` (a `*/1 * * * *` cron fallback, for a kick lost to a broker hiccup) run `ProcessOutboxEntryUseCase` in the `worker` process: it loads the outbox row, persists it to the audit log, then calls `bus.dispatch_stored()` for any type-specific subscriber. A failed handler leaves the row unprocessed for the next sweep to retry — the audit-log write itself has already committed either way. `prune_outbox_task` deletes processed rows older than 14 days on a daily cron. The audit log itself keeps money, access, admin and security events for good; `prune_event_log_task` drops the noisy panel and infrastructure types listed in `event_log/retention.py` after 90 days (`tests/modules/event_log/test_retention.py` makes every new subscription or infrastructure event pick a side). Recording a `UserDeletedEvent` anonymizes that customer's log and outbox entries in the same transaction.
- This makes delivery genuinely cross-process (the write happens wherever the usecase runs; persistence and dispatch happen in `worker`) and durable — a crash between commit and dispatch can't lose the event, since the row is already there for the next sweep.
- `app/worker/lifespan.py` calls `app/worker/subscribers.py`'s `register_all_subscribers()` on startup and `EventBus.shutdown()` on teardown. Subscribers live in each module's `subscribers.py` (event classes stay in `events.py`), listed explicitly there — `core` never imports a module. `api/lifespan.py` and `app/telegram/lifespan.py` don't register any — since `dispatch_stored()` only ever runs from the outbox sweep in `worker` (see above), a registration in either process would sit unused.
- A usecase enqueues a worker task through a typed `*Dispatch` port (`modules/<domain>/dispatch.py`, provided in `di.py` as the task cast to the port) inside `await uow.after_commit(...)`, so nothing is sent for a transaction that rolls back; outside a transaction the callback runs at once. Never import a `tasks.py` from a usecase.
- Conventions for writing events/subscribers and the error-isolation rule: [docs/architecture/events.md](docs/architecture/events.md).

## Roles & Permissions

Conventions, the `Permission`/`PermissionPolicy`/`ROLE_PERMISSIONS` machinery, and the router-vs-usecase enforcement split: [docs/architecture/permissions-roles.md](docs/architecture/permissions-roles.md).

- `Role.DEV` and `Role.PREVIEW` existed in the pre-rebuild codebase and were removed (2026-08-13) rather than carried forward. `DEV` was the auto-demotion target for a former `OWNER` on ownership transfer (`old_owner.role = Role.DEV` in the old `registration.py`), granted full permissions same as `OWNER` — a role-tier stand-in for "full access, not the current owner." `PREVIEW` was marked `# TODO: Implement demo Bot instance` and never had a creation path either. Neither had any reference left in the new `backend/app/` tree before removal (verified by grep).
- Per-user permission overrides are built: `Permission.ADMINS_MANAGE` is granted only to `OWNER`/`SYSTEM` by default (`core/security/permissions.py`'s `ROLE_PERMISSIONS`) — the first place `ADMIN` and `OWNER` diverge. `GRANTABLE_PERMISSIONS` is `frozenset(PERMISSION_METADATA)` — every `Permission` except `PUBLIC`/`ADMINS_MANAGE`/`API_TOKENS_MANAGE`/`OWN_ACCOUNT_MANAGE` (the last is in every privileged role's default, and revoking it breaks `GET /users/me`) and the OWNER-only `PRICING_RATES_MANAGE`/`PRICING_ANCHOR_MANAGE`/`USERS_UNBLOCK_BLACKLIST_MATCHES`/`BACKUPS_RUN_DOWNLOAD` (a DATABASE dump subsumes every other read permission)/`NOTIFICATION_VAPID_KEYS_GENERATE` (regenerating keys drops every device's push subscription)/`OVERVIEW_RECAP_VIEW`/`TRANSACTIONS_UNRATED_RATE`, the set an `OWNER` may grant/revoke per admin (`TRANSACTIONS_REFUND`/`TRANSACTIONS_REFUND_PREVIEW` — Telegram Stars refund and its preview — are grantable but in OWNER's default only, never on a token) (API tokens get a narrower `TOKEN_GRANTABLE_PERMISSIONS`: no login/bot/gateway-credential changes, no irreversible or bulk-overwrite actions — the catalog's `token_grantable` flag drives the token picker; dashboard-only metadata routes — `/overview*`, `/gateways/catalog`, `/permissions/catalog` — take `require_admin_user`. A token stores Remnawave-style `scopes` — `*`, `<resource>:*`, `<resource>:read|write` or a single permission — expanded on every request by `expand_token_scopes`, so new permissions reach resource-scoped tokens and exclusions reach every token; `expires_in_days` is mandatory) via the `permission_grants`/`permission_revokes` JSONB columns on `User`. 2026-08-24: composite permissions that gated more than one usecase were split into one `Permission` per usecase (matching Remnawave's per-endpoint API-token scope granularity) — see [docs/architecture/permissions-roles.md](docs/architecture/permissions-roles.md)'s granularity rule. `PermissionPolicy.effective_permissions(actor)` merges role default with per-user overrides: `(role_default | grants) - revokes`. `OWNER` manages this from the Admins page (`modules/users/usecases/`, `/admins*` + `/users/me/security` endpoints). This is *why* `DEV` was dropped instead of kept: its whole purpose (a role tier representing "full access without being `OWNER`") is subsumed once you can just grant an `ADMIN` every permission directly.
- IP allowlist: each privileged account (including `OWNER`) can set a self-service `ip_allowlist`, enforced on every authenticated request via `get_current_actor` (`api/dependencies/public.py`) — applies to every role, no exemption.
- **Cabinet sign-in** (`modules/cabinet_auth/`): `cabinet_auth/api/router.py` is another zero-session router (sign-in steps), its authenticated routes in `public_router.py` (and `legal`'s `cabinet_router.py`, `/cabinet/legal/*`) use `api/dependencies/public.py`'s `get_cabinet_user` (a real `UserDto`; `require_admin` answers a cabinet session with 403 `SESSION_AUDIENCE_MISMATCH`, even for a staff member). Telegram identity = `users.telegram_id` everywhere — no `OAuthIdentity` rows for `TELEGRAM`. `users.email` holds only proven addresses, stored lowercased (CHECK `ck_users_email_lowercase`). The cabinet's reverse proxy forwards the client IP in `X-Cabinet-Client-IP`; it is trusted only together with `X-Cabinet-Proxy-Secret` matching `CABINET_PROXY_SECRET`, otherwise the usual `X-Forwarded-For`/socket-peer resolution applies.

### Repository and infrastructure rules

- A row maps to its DTO in `def _to_dto(self, row)` / `_to_<entity>_dto(self, row)` — an instance method, no staticmethod, lambda or module function — and is `XDto.model_validate(row, from_attributes=True)` unless a value is computed or JSON decoded.
- DTO base: `BaseDto` (+`TimestampMixin`) for a table row; `@dataclass(frozen=True, kw_only=True)` for usecase inputs and results; a plain pydantic `BaseModel` only where pydantic validates or serializes (JSONB, external payloads, the analytics Redis cache).
- `get_by_id` (and `get_by_id_for_update`) raises `NotFoundError`; a lookup that may miss is `find_*`, a `skip_locked` claim is `try_lock`.
- A list of ids filters through `core.db.filters.in_ids(column, ids)` (one `= ANY(array)` bind), never chunked `IN`.
- Settings-style tables use `core.db.singleton.SINGLETON_ID`.
- DI: a task-backed `*Dispatch` is provided at `Scope.APP`; a class whose constructor DI can fill is `provide(X)` under the snake_case name of the class, not a factory method; one class is `provide`, several are `provide_all`.
- A Bot API call outside the `telegram` process is `bot.call("<method>", ...)` (or `bot.upload`/`bot.download`) on `core.telegram_api.bot_client(...)` with plain dicts, never an aiogram import; failures caught as `BOT_API_ERRORS` and described by `bot_api_error_text`, Telegram's own refusal is `BotApiRefusedError` (`error_code`, `description`); a 429's wait is its `retry_after`, and every wait is capped by its caller. Tests fake the session with `tests/fakes/telegram_bot.py`'s `FakeBotSession`/`use_fake_bot` (replies keyed by method name, `getMe`); bot handler tests use `tests/fakes/aiogram_bot.py`'s `FakeAiogramSession`.
- Every date the bot shows a customer goes through `telegram.i18n.format_datetime`/`format_date`.
- A repository takes `now` from its caller when the caller already has one; new code passes it, existing `datetime_now()` calls are aligned when touched.

## Database: columns vs JSON

Column by default; JSON (`postgresql.JSONB`) only for an unowned external format passthrough or an always-atomic settings bundle — see [docs/architecture/db-models.md](docs/architecture/db-models.md) for the full rule. `BotSettings`/`OAuthSettings` are real columns for exactly this reason: each field is independently meaningful, not a bundle. Matches Remnawave's own schema (`prisma/schema.prisma`): the overwhelming majority of fields are typed columns, even enums (stored as `String` with a `// ENUM: ...` comment, not a Postgres enum type); `Json` shows up only for Xray/host protocol param blobs, settings bundles, and open metadata fields — never for anything queryable.

## Migrations

Alembic with a **version chain** (since 2026-11-06), numbered revisions: `1000_initial_schema.py` (`revision="1000"`, `down_revision=None`) is the released baseline — never edit or regenerate it, deployed databases (fresh installs and migrated legacy shops) are stamped `1000`. `process_revision_directives` in `migrations/env.py` numbers each new revision head + 1 (`1001_<slug>.py`, `1002_…`); `0001`–`0046` belong to the old app's chain (`app/cli/legacy/migrations`) and must never be reused — the entrypoint guard tells old databases from new ones by revision id. Every schema change is `uv run alembic revision --autogenerate -m "<what>"` against a database already at the head (not an empty one), reviewed by hand (autogenerate misses enum value additions and renames), with a working `downgrade`. `tests/core/db/test_migration_chain.py` pins one base (`1000`) and one head; `test_schema_drift.py` catches a model change without a revision.

## Rules for every change

### Layers

- **A repository reads and writes rows, nothing else.** No business decisions (`if` on "opted out", "retry allowed", "consent valid"), no events, no provider calls, no constructing other repositories. That logic goes in a usecase or a pure function in a module file. A repository past ~300 lines usually hides a usecase.
- **Everything is built by DI.** No `SomeRepository(self.session)` or `SomeRepository(other_repository.session)`. Exceptions, all because no container exists or the object owns its own sessions: `app/cli/`, the pre-container settings read (`modules/settings/bootstrap.py`), and `Scope.APP` caches/claims that hold a session maker (`telegram/settings_cache.py`, `telegram/dialogs/config_cache.py`, `telegram/i18n.py`, `WaitlistClaims`).
- **No `_private` names imported across files.** If you need it, it needs a public API or a port.
- **A usecase does one thing.** An input that means "one item, or the whole batch when `None`" is two usecases.
- **Codes stored or compared as data (statuses, failure reasons) are an enum** declared once, like `ErrorCode`. A set of codes that "need attention" exists in exactly one place.

### Reuse before writing

Search the module and `app/core` first. Often re-implemented: `subscriptions.get_owned_target` (a customer's own subscription), `users.get_visible_target`/`visible_user`/`assert_manageable` (another user, hidden staff), `users.detail_roles` (which roles an actor may see — never a hand-written `Role.in_([...])`), `core.events.changed_fields`, `core.db.filters.in_ids`, `core.constants` page/search limits, `telegram.i18n.format_datetime`/`format_date`, `core.telegram_api.bot_client`.

### Opt-in features

- Work a feature adds to hot paths (bot screens, checkout, fulfillment, webhooks) runs only after checking its flag.
- Changing shared code is fine; a PR lists every such change under "What changes for shops that don't enable this".

### Money

- The provider idempotency key is stored before the request is sent and reused on retry; an ambiguous request is never re-sent after the provider's key retention window — the outcome becomes "unknown" and an admin sees it.
- An order is credited only after the provider's API confirms reference, amount, currency and status (see `gateways/base.py`'s `confirm`); a webhook body is a lookup hint.
- A new stateful payment entity documents (in its PR) its behavior on: refund, partial refund, manual renewal by another method, a payment in flight, plan change, price change, gateway credentials change or disable, payments disabled, user blocked, account merge, user deletion.
- Two paths that can each charge for the same period (automatic and manual) check each other before sending, including a payment still in flight.
- Saved payment methods, tokens and keys are `EncryptedString`/`SecretStr`, write-only in the API. Logs carry status codes and our own reason codes, never provider response bodies.

### Customer consent and contractual text

- Consent to future charges (auto-renewal, a saved card) is explicit, off by default and separate from accepting the offer.
- Making a purchase conditional on such consent is the shop owner's business decision, never a default.
- Text a customer agrees to is editable by the shop owner (`legal` documents or translation keys), never a Python string; the exact text shown is stored with the consent.
- A customer-facing change covers the bot and the web cabinet (separate repository), or degrades to "unchanged" where it isn't implemented — never to "broken".

### Events and notifications

- Events are published only through the injected `EventPublisher`; nothing outside `core` writes `EventOutboxEntry`.
- A new event type is either listed in `event_log/retention.py` (pruned after 90 days) or kept for good on purpose; routine per-customer events (reminders, schedules) are pruned.
- Admin notification groups get events an admin acts on, not a message per customer per billing cycle.

### Configuration

- Environment variables are for deployment (hosts, ports, pools, infrastructure secrets). Business settings live in the dashboard (database). A value nobody needs to change is a `Final` constant.
- Terms a customer agreed to never change because an operator edited `.env`.

### Telegram bot

- Never append to `render_window_text`'s result: that skips HTML validation and the 1024-character caption limit. Extra blocks are `frg-*` variables of the window.
- A window's buttons go through the dialog catalog (`ConfigKeyboard`) so the shop owner can edit them. A button the bot builds in code (list items, flow steps, `/terms`) takes its label from a `btn-*` key through `telegram/dialogs/rendering.py`'s `label_with_icon` (`style=LabelIcon(...)` in a dialog), so the translations page edits its text and icon; never a literal label.

### Dashboard code

- Lists of entities use `ListRow`; a raw `<table>` only for a data matrix (pricing, retention). Raw `<button>`/`<input>` only for drag handles, file inputs, inline text links and tab strips.
- A field kind added to a generic component (a settings form) stays generic, with no one feature's flags wired into it.
- Money goes through `shared/lib/format`'s `formatMoney`; a full date or date-time shown to the admin through `shared/lib/relative-time`'s `formatDate`/`formatDateTime`/`formatTime`. Counts use `toLocaleString(language)`, and short chart labels may call `toLocaleDateString` with their own options. A page size comes from the entity's `api.ts` constant, not a literal.

### Tests

- Cover what would cost money or access if it broke: every state transition, every refusal, concurrent paths (webhook vs poller, manual vs automatic).
- Anything transactional is tested against the real test database — a flush-only test can't catch a missing commit. Providers are mocked at the HTTP boundary; tests never make live charges.

## Frontend

Feature-Sliced Design: `app/` (providers, router, styles) → `pages/` → `widgets/` → `features/` → `entities/` → `shared/` (api client, lib, types). Path aliases `@app`/`@pages`/`@widgets`/`@features`/`@entities`/`@shared` — configured in both `vite.config.ts` and `tsconfig.app.json` (keep them in sync). Tailwind CSS v4 via `@tailwindcss/vite` (no PostCSS config file). Routing via `react-router`; auth guards in `shared/lib/route-guards.tsx`.

**Layers**: a layer imports only layers below it — enforced by `no-restricted-imports` overrides in `.oxlintrc.json` (`shared` imports nothing above it, `entities` nothing from `features` up, and so on) plus `import/no-cycle`. Deliberate relaxation of FSD: slices of the same layer may import each other (a feature using another feature's dialog), as long as no cycle forms; a card that opens another entity goes through `useOpenEntity()` instead of importing its dialog.

**Imports**: cross-slice imports always go through a `@alias`, never a relative `../` — enforced by oxlint's `import/no-relative-parent-imports` (`.oxlintrc.json`). Type-only imports use a separate `import type { ... }` statement, never an inline `type` modifier inside a value import — enforced by `typescript/consistent-type-imports` (`prefer: "type-imports"`). Group/order within a file (external packages, blank line, `@alias` imports) has no lint rule (oxlint's `import` plugin has no `order` rule) — follow existing files, enforced by review only. `npm run lint` ends with `knip` (`knip.json`): an unused file, export or dependency fails it; a type used only in its own file may stay exported, an export kept for planned work carries `/** @public */`.

**i18n**: `react-i18next`, resources bundled directly (`shared/i18n/locales/{en,ru}.json`), not lazy-loaded over HTTP — deliberately lighter than Remnawave's stack (`i18next-http-backend` + `i18next-browser-languagedetector` + typesafe-i18n tooling), which isn't worth the weight at this app's current size (a handful of pages). Language persists to `localStorage` (`remnashop_language`) via a `languageChanged` listener in `shared/i18n/index.ts`, detected on boot from that key or `navigator.language`, falling back to `en`. `SUPPORTED_LANGUAGES`/`SupportedLanguage` (currently just `en`/`ru`) live in `shared/i18n/index.ts` — add a language by adding a locale JSON file and one entry there, plus a label in `widgets/language-picker/LanguagePicker.tsx`'s `LANGUAGE_LABELS`. Keys are typed (`shared/i18n/i18next.d.ts` binds `en.json` as the resource type), so `tsc` rejects an unknown key; a key built from a runtime value (API enum, event type) is cast `as ParseKeys`, one built from a constant gets `as const`/a `ParseKeys`-typed field instead. `npm run lint` also runs `scripts/check-locales.mjs`: every locale has en's keys, its language's plural forms (`Intl.PluralRules`; ru `_other` = `_few`, for fractions) and en's `{{variables}}`. Words reused across pages (`cancel`, `save`, `saved`, `delete`, `reset`, `create`, `edit`, `add`, `yes`/`no`, `none` = "—", `errors.generic`) live in `common.*`; a domain key holds only context-bound text. Text style: a message shown in a toast or as an error ends with a period (`apiErrors.*` too), a label/button/title/placeholder doesn't; en uses “curly quotes”, `Failed to …`, `admin`; ru uses «ёлочки», `ё`, «администратор» in prose (`админ` only on space-tight buttons and menu items), «панель управления» for the dashboard. Every user-facing string in a component must go through `useTranslation()`'s `t()`, not a hardcoded literal — the `LanguagePicker` widget is on both `LoginPage` (top-right, pre-auth) and `Header` (all dashboard pages), so nothing should be reachable without it applying.

**Type scale**: Tailwind's default steps, no arbitrary `text-[Npx]` — `text-xs` 12px (hints, meta, mono ids, `Badge`/`Tag`, uppercase `EYEBROW_CLASS`), `text-sm` 14px (body, fields, buttons, menu items), `text-base` 16px (card and dialog titles, `STAT_VALUE_CLASS`), `text-lg` 18px (page title in the header), `text-xl` 20px (`SCREEN_TITLE_CLASS`), `text-2xl` 24px (`KPI_VALUE_CLASS`); 11px only for counters and mini badges. Exceptions: the header's account name and role (13/12px, so its `leading-tight` isn't overridden by the scale's line heights), emoji glyph sizes, avatar initials, `RecapCard` (rendered to an image). A `text-sm`/`text-xs` class sets its own line height, so inside a `leading-*` block it overrides that leading.

**Tooltips**: never the native `title` attribute — it's unstyled, delayed, invisible on touch and can't be themed. If a hint has to be visible, build it with the app's own popover/tooltip markup.

**Accessibility markup**: no screen-reader-only attributes — no `aria-label`, `aria-hidden`, `aria-pressed`/`aria-checked`, `aria-haspopup`, `aria-modal`, `aria-describedby` or `role="..."` added for announcement's sake (removed project-wide 2026-10-02). ARIA stays only where CSS or JS reads it as state: `aria-invalid` (error ring in glass `Input`/`TextArea`, border in `TextInput`), `aria-expanded` on `ActionMenu`'s trigger (row `z-20` under an open menu in Users/Admins), `aria-selected` in `DialogTabs` and the router's own `aria-current` (active-tab scroll). A new state hook for styling or a selector uses `data-*` (`data-dialog`, `data-disabled`), not ARIA.

**Shared UI**: build from `shared/ui` primitives, not hand-written class strings — `Button` (glass variants `glass`/`glassAccent`/`glassSolid`/`glassDanger` for dialog and form actions, `secondary` for card-header actions and buttons beside a field (semibold) — all 14px; sizes `sm` 32px in list rows, `md` 36px, `field` 38px beside a 38px input), `IconButton` (size follows the container: equal inset on every side, concentric corners), `Badge` (status, `tone`) vs `Tag` (counts/metadata), `glass/Input`'s `Input`/`PasswordInput`/`CopyInput`/`TextArea` (form fields; `TextInput` is the dialog editor's link popover's only) vs `SearchField` (filters only), `glass/Field` (label + control + hint), `glass/Section` (a settings card) and `glass/DialogCard` (`list`/`form` blocks inside a glass dialog), `DialogHeader`, `DialogTabs`, `ChoiceChip`, `KpiTile`, `ListRow` (a table row that opens details), `glass/Row` (`onClick` + `expanded` for a row that folds out), and `shared/ui/classes.ts` (`POPOVER_CLASS`, `EYEBROW_CLASS`) where structure differs too much for a component. `className` on these is layout only — no Tailwind class that fights the component's own (no `tailwind-merge` in the project). `BotSettingsForm` keeps its own editor styling on purpose. Anything pressable goes through `Pressable` (`as` button/link/a/div): it positions the element and adds the tap `Ripple`, so pages and features hold no raw clickable `button`/`a`/`onClick` div (inline text links and drag handles excepted) and no `<Ripple />` of their own; no scale "bounce" on press or hover. Every primitive is shown on `/dashboard/debug` (`pages/debug/`); a new variant or a unification pass goes there first ("before → after"), code changes after sign-off.

## Typing

Optional values use `typing.Optional[X]`, never PEP 604's `X | None`; other unions use `typing.Union[X, Y]`, not `X | Y`. Applies to backend Python code only (`ruff` has no rule to enforce this direction — it's discipline, not lint-enforced).

## Constants

Every module-level constant — public or `_private` — is annotated `Final[T]`, no exceptions. Shared constants live in `core/constants.py`; a constant used only within one module lives at the top of the file that owns it (not duplicated across the files that consume it). If the same literal is needed in more than one place, it gets a name and a single source, not repeated copies.

## Commit messages

English only. Body: past-tense `- ` bullets starting with a lowercase letter, blank line after the subject line. Never add a `Co-Authored-By` line.

## Comments & docstrings

Default to none: a comment says *why*, never *what* the code already shows. When a comment earns its place, it also has to *read* like it was written by someone who works here, not by a model narrating its own output. Concretely:

- No hedging/filler: "It's worth noting that", "Please note", "This is important because", "essentially", "simply" — say the fact, not the fact wrapped in throat-clearing.
- No restating the code in prose ("This function creates a user" above `create_user`) and no restating the comment's own existence.
- No referencing the current task/fix/PR ("added to fix the race condition", "updated for the new auth flow") — that belongs in the commit message, not the code; it rots the moment the code changes again.
- Terse fragments over complete grammatical sentences where a fragment says the same thing — `# guards against double-submit`, not `# This guards against the possibility of a double submission occurring.`
- If you wouldn't say it out loud to a coworker in that exact phrasing, don't write it.
- No provenance: don't cite another project, the pre-rebuild codebase or `main` as the reason for a choice ("mirrors Remnawave's…", "ported from `main`", "same as the old bot") — state the reason itself; a borrowed pattern worth recording goes in AGENTS.md/docs. Facts about Remnawave as the integrated panel (API units, id types, conventions we must match) are fine.
